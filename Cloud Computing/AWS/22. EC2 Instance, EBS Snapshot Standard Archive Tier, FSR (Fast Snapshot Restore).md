
## Snapshots
---
![[22Snapshots.png]]


**Snapshots** in AWS are a fundamental backup and disaster recovery feature for **Amazon EBS (Elastic Block Store) volumes**.

In simple terms, an **EBS Snapshot is a point-in-time copy of your EBS volume**, saved to durable and inexpensive Amazon S3 storage.

---

### Key Characteristics of EBS Snapshots

#### 1. **Incremental Backups**
This is the most important concept to understand.
*   When you create your **first snapshot** of a volume, it copies all the data that has been written to the volume.
*   Subsequent snapshots only save the **blocks that have changed** since the last snapshot.
*   **Benefit:** This saves storage space and reduces the time and cost required to create subsequent backups.

**Visual Example:**
*   **Day 1 (Snapshot A):** Backs up blocks 1, 2, 3, 4.
*   **Day 2 (Snapshot B):** Only block 3 changed. Snapshot B only saves the new block 3 and references the unchanged blocks (1, 2, 4) from Snapshot A.
*   **Day 3 (Snapshot C):** Blocks 1 and 4 changed. Snapshot C saves the new blocks 1 and 4 and references the unchanged blocks from previous snapshots.

Even if you delete Snapshot A, the data for blocks 2 (which hasn't changed) is preserved in Snapshot C's chain. AWS manages this complexity for you.

#### 2. **Durability and Storage**
*   Snapshots are stored automatically in **Amazon S3**, which is designed for 99.999999999% (11 9's) durability.
*   You don't need to manage the S3 buckets or objects; it's all handled transparently by the EBS service.

#### 3. **Crash-Consistent**
*   Snapshots are "crash-consistent," meaning they capture the data on disk as if the system crashed at that exact moment.
*   For database applications (like MySQL or Oracle), it's recommended to ensure data is flushed from memory to disk before the snapshot. This can often be done by pausing I/O or using application-specific freeze tools. Alternatively, you can use the **AWS Backup** service, which provides application-consistent backups for many services.

---

### Primary Use Cases for Snapshots

#### 1. **Data Backup and Recovery**
*   **Backup:** Regularly scheduled snapshots (e.g., daily, weekly) protect your data from accidental deletion, corruption, or application error.
*   **Recovery:** If data is lost, you can create a new EBS volume from a snapshot and attach it to an instance to restore the data.

#### 2. **Disaster Recovery (DR)**
*   Snapshots can be **copied to another AWS Region**.
*   In the event of a regional outage, you can quickly launch new EC2 instances in the other region using volumes created from these copied snapshots.

#### 3. **Creating AMIs (Amazon Machine Images)**
*   To create a custom AMI (a template for launching new EC2 instances), AWS takes snapshots of the instance's root EBS volume and any other attached volumes in the background.

#### 4. **Volume Migration and Resizing**
*   You can create a new, larger (or smaller) EBS volume from an existing snapshot to easily scale your storage.
*   You can migrate a volume to a different Availability Zone by creating a snapshot and then creating a new volume from that snapshot in the target AZ.

#### 5. **Data Sharing**
*   You can **share a snapshot** with another AWS account or make it public. The other account can then create their own volume from your snapshot.

---

### How to Create and Use Snapshots

#### Creating a Snapshot
You can create a snapshot in several ways:
1.  **Manually:** Via the AWS Management Console, CLI, or SDK.
2.  **Automated:** Using **Amazon Data Lifecycle Manager (DLM)** to define policies for creating, retaining, and deleting snapshots automatically.
3.  **Via AWS Backup:** A centralized service to manage backups across multiple AWS services (EBS, EC2, RDS, DynamoDB, etc.).

#### Restoring from a Snapshot
The process to restore data is straightforward:
1.  **Locate the Snapshot:** Find the desired point-in-time snapshot in the EBS console.
2.  **Create a Volume:** Select the snapshot and choose "Create Volume." You can specify a new size, volume type (e.g., gp3), and Availability Zone.
3.  **Attach the Volume:** Attach the new volume to an EC2 instance. You may then need to mount the filesystem (for non-root volumes) to access the data.

---

### Cost Model for Snapshots

*   You are billed for the **total amount of data stored in S3** for your snapshots.
*   Because snapshots are incremental, the cost of each subsequent snapshot is typically much lower than the first.
*   **Example:** If you have a 100 GB volume and only change 5 GB per day, your first snapshot will be ~100 GB, but your daily snapshots thereafter will only consume ~5 GB of new storage each.

---

### Best Practices

1.  **Use Descriptive Tags:** Tag your snapshots with names, creation dates, and purposes (e.g., `Daily-Backup`, `Pre-Patch-Update`) for easy management.
2.  **Automate with DLM:** Don't rely on manual snapshots. Use Data Lifecycle Manager to create a regular backup schedule (e.g., daily at 2 AM) and a retention policy (e.g., keep daily backups for 30 days, monthly backups for 12 months).
3.  **Copy Critical Snapshots to Another Region:** For important disaster recovery plans, regularly copy your snapshots to a different geographic region.
4.  **Secure Your Snapshots:** By default, snapshots are private. Be cautious when sharing them publicly or with other accounts.

**Key Takeaway:** **EBS Snapshots are incremental, point-in-time backups of your EBS volumes, stored durably in S3. They are the primary mechanism for backing up EC2 instance data, enabling disaster recovery, and creating templates for new servers.**


## Images

---
![[22-Images.png]]

 An **AMI (Amazon Machine Image)** is a fundamental building block in AWS EC2.

Think of an AMI as a **template** or a **blueprint** for a virtual server. It contains all the information needed to launch an EC2 instance.

A good analogy is that an **AMI is like a DVD installation disc** for an operating system and pre-installed software, while an **EC2 instance is the actual running computer** you've installed it on.

---

### What's Inside an AMI?

An AMI includes the following key components:

1.  **A Root Volume Template:**
    *   This contains the operating system (e.g., Amazon Linux, Windows Server, Ubuntu), application servers, and any other software.
    *   It's typically based on a snapshot of an EBS volume.

2.  **Launch Permissions:**
    *   Controls which AWS accounts can use the AMI to launch instances. AMIs can be:
        *   **Public:** Provided by AWS or the community (e.g., Amazon Linux AMI, Ubuntu AMIs).
        *   **Private:** Only your account can use it.
        *   **Shared:** Explicitly shared with specific AWS accounts.

3.  **Block Device Mapping:**
    *   Specifies the volumes to attach to the instance when it's launched. This includes the root volume and any additional EBS volumes or instance store volumes.

---

### Why are AMIs Important? Key Use Cases

#### 1. **Booting Standardized Instances**
This is the primary use. When you launch an EC2 instance, the very first step is to choose an AMI. This determines the OS and initial software state of your server.

#### 2. **Creating Golden Images (Baking AMIs)**
This is a critical practice for achieving consistency, scalability, and fast boot times.
*   **Process:** You launch an instance from a base AMI (e.g., Amazon Linux), install all your necessary applications, dependencies, and configuration files, and then create a **custom AMI** from this configured instance.
*   **Benefits:**
    *   **Consistency:** Every instance launched from your "golden image" is identical. No more "it worked on my machine" problems.
    *   **Fast Scaling:** When scaling out (e.g., in an Auto Scaling Group), new instances can launch in seconds, fully configured and ready to serve traffic, instead of taking minutes to install and configure software.
    *   **Immutable Infrastructure:** You can version your AMIs, promoting a tested, immutable server image through development, staging, and production.

#### 3. **Disaster Recovery & Migration**
*   You can create an AMI of a critical server and copy it to another AWS Region. If the primary region fails, you can quickly launch instances from the AMI in the backup region.
*   You can also migrate workloads from on-premises or other clouds by creating a VM import process that results in an AMI.

#### 4. **Pre-Configured Solutions & Marketplaces**
*   AWS and partners offer AMIs pre-configured with complex software stacks (e.g., WordPress, SQL Server, SAP). This lets you launch a fully functional application in minutes.
*   The **AWS Marketplace** allows you to use and pay for commercial software directly through AMIs.

---

### AMI Sources: Where Do They Come From?

1.  **AWS Provided AMIs:** These are maintained by AWS and are the most common starting point. They include:
    *   Amazon Linux (various versions)
    *   Windows Server
    *   Ubuntu, Red Hat Enterprise Linux, SUSE Linux
    *   These are kept up-to-date with security patches.

2.  **AWS Marketplace AMIs:** Pre-configured by software vendors (e.g., Cisco, Fortinet, Splunk). These often have additional hourly or annual software charges.

3.  **Community AMIs:** Public AMIs created by other AWS users. **Use with caution** as they are not vetted by AWS for security.

4.  **Your Own Custom AMIs:** AMIs you create from your own configured instances.

---

### The AMI Lifecycle

1.  **Create:**
    *   Start with a base AMI, launch an instance, and configure it.
    *   Use the EC2 console, CLI, or tools like `Packer` to create a new AMI from the instance. This action automatically creates snapshots of the instance's EBS volumes.

2.  **Launch:** Use your custom AMI to launch new, identical EC2 instances.

3.  **Deregister:** When an AMI is no longer needed, you **deregister** it. This removes the AMI definition from your account.
    *   **Important:** Deregistering an AMI **does not delete the underlying EBS snapshots**. You must delete those snapshots separately to fully clean up and stop incurring storage costs.

---

### AMI Costs

*   **The AMI itself (the metadata) costs nothing.**
*   You pay for the **underlying EBS snapshots** that the AMI references. You are billed for the total storage size of these snapshots in S3.
*   For Marketplace AMIs, you may pay an additional hourly or upfront software charge on top of the standard EC2 and EBS costs.

### Best Practices

1.  **Use Golden Images:** For production, always use a custom, hardened AMI rather than configuring instances manually after launch.
2.  **Keep AMIs Lean:** Only install what is necessary on the base image to reduce boot times and minimize the attack surface.
3.  **Patch and Update Regularly:** Create a process to regularly update your base AMIs with the latest security patches and create new versions.
4.  **Use Tools like Packer:** HashiCorp Packer is an industry-standard tool for creating identical machine images across multiple platforms from a single source configuration. It automates and codifies the AMI creation process.

**Key Takeaway:** An **AMI is a template that packages the software configuration (OS, application, settings) for an EC2 instance.** It is the key to achieving consistency, automation, and rapid deployment in your AWS environment.
