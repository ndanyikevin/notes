
## 🧩 What Is a **Key Pair** in AWS?

A **key pair** in AWS is a **set of two cryptographic keys** (a public key and a private key) that AWS uses to **securely connect to your EC2 instance** — usually via **SSH (Linux)** or **RDP (Windows)**.

---

### 💡 In plain terms:

> A key pair is your **login credential** to your EC2 instance — like your house key.
> 
> - The **public key** stays with AWS (on the instance).
>     
> - The **private key** stays with you (on your computer).
>     

Together, they prove your identity when connecting — no password needed.

---

## 🧠 How It Works

1. When you **create an EC2 instance**, AWS asks for a **key pair**.
    
2. You can:
    
    - **Create a new one**, or
        
    - **Use an existing one**
        
3. AWS:
    
    - Stores the **public key** in the instance (under `~/.ssh/authorized_keys` on Linux)
        
    - Gives you the **private key file** (`.pem` file) to download once
        
4. To connect via SSH:
    
    ```bash
    ssh -i my-key.pem ec2-user@<public-ip>
    ```
    
    - `my-key.pem` = your private key
        
    - AWS checks it matches the stored public key
        

If they match → ✅ **access granted**

---

## 🧾 Key Pair Example

When creating an EC2 instance:

- AWS generates:
    
    - **Public key** → stored inside the instance
        
    - **Private key (PEM file)** → downloaded to your machine
        

```text
my-key.pem
```

Keep that `.pem` file safe — it’s your only way to SSH into that instance.

---

## ⚠️ Security Tips

|Rule|Why|
|---|---|
|🔒 **Never share your `.pem` file**|Anyone with it can log into your server|
|☁️ **Store backups securely (like AWS Secrets Manager)**|If you lose it, you lose access|
|🔐 **Use file permissions**: `chmod 400 my-key.pem`|Required by SSH to prevent misuse|
|🔁 **Rotate keys periodically**|In case of leaks or personnel changes|

---

## 💡 For Windows Instances

- AWS uses the **key pair** to **decrypt the Administrator password**.
    
- You download the password file and use the private key to decrypt it locally.
    

---

## ✅ In summary:

> A **key pair** is a combination of a **public key (stored in AWS)** and a **private key (.pem file you keep)** used to securely log in to EC2 instances without passwords.

---

## How to manage EC2 Instance Users.
---
## 🎯 Goal

You want to manage **user access to EC2 instances** securely — possibly using both:

- **Key pairs** (SSH keys for Linux or RDP for Windows), and
    
- **Active Directory (AD)** for centralized identity and access control.
    

These are **two different layers** of authentication — you can use one or both depending on your setup.

---

## 🧩 1️⃣ Managing Users with **Key Pairs**

### 🧠 Basics:

Each EC2 instance can have multiple **authorized public keys**, one per user.  
So, if you have multiple developers or admins:

- Each user generates their **own key pair**:
    
    ```bash
    ssh-keygen -t rsa -b 4096 -C "username"
    ```
    
- They give you their **public key** (the `.pub` file).
    
- You add that key to the instance’s `~/.ssh/authorized_keys` file under their username.
    

✅ Result:  
Each person logs in with their **own private key**, no shared credentials.

---

### 🛠️ Example

For user _Alice_:

```bash
echo "ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC..." >> /home/alice/.ssh/authorized_keys
```

Then she connects:

```bash
ssh -i alice-key.pem alice@<ec2-public-ip>
```

AWS doesn’t manage these keys automatically — you control them at the OS level or automate it using tools like:

- **AWS Systems Manager Session Manager**
    
- **AWS IAM Instance Connect**
    
- **Cloud-init** or **Ansible** (to push user keys)
    

---

## 🧩 2️⃣ Managing Users with **Active Directory (AD)**

### 💡 Why Use AD?

Key pairs are great for small teams, but at scale, you want **centralized login management**:

- Single sign-on (SSO)
    
- Role-based access
    
- Password and account lifecycle policies
    

That’s where **Active Directory** (Microsoft AD) or **AWS Directory Service** comes in.

---

### 🧠 How It Works

AWS offers **AWS Directory Service** — which lets you integrate EC2 instances with AD.

You have 3 main options:

|Option|Description|Use Case|
|---|---|---|
|**AWS Managed Microsoft AD**|A fully managed AD hosted by AWS|Enterprises using Windows|
|**AD Connector**|Connects to your on-premises AD|Hybrid setups|
|**Simple AD**|Lightweight directory for small orgs|Small teams/labs|

---

### 🖥️ For Windows EC2 Instances:

- Join your instance to the **Active Directory domain**
    
- Then AD users can **RDP using their AD credentials** (username + password)  
    → No need for `.pem` files
    

This is managed through:

- **AWS Directory Service**
    
- **EC2 launch options** → “Domain join directory”
    

✅ Users are now authenticated by AD instead of key pairs.

---

### 🐧 For Linux EC2 Instances:

You can join them to AD using:

- **SSSD (System Security Services Daemon)**
    
- **realmd** or **sssd-ad provider**
    

Then, users can log in with:

```bash
ssh user@instance
```

and be authenticated via **AD Kerberos**, not SSH key.

---

## 🔐 Combining Both (Hybrid Setup)

Some organizations use both:

- **Key pairs** for admins (low-level access)
    
- **AD authentication** for developers or domain users
    

This gives:

- Centralized user management (AD)
    
- Emergency SSH access (keys)
    
- Better audit trails
    

---

## 🧾 Summary Table

|Method|Auth Type|Best For|Notes|
|---|---|---|---|
|**Key Pairs**|SSH keys|Small teams, admins|Manual, decentralized|
|**Active Directory**|Central user accounts|Enterprises, domain control|Managed via AWS Directory Service|
|**Hybrid (Both)**|SSH + AD|Mid-to-large orgs|Combine flexibility and control|

---

✅ **In short:**

> - Use **Key Pairs** for small-scale SSH access.
>     
> - Use **Active Directory (AWS Managed AD or AD Connector)** for centralized, scalable login management.
>     
> - Combine both for the best of both worlds.
>     


## Cluster Network Groups
---
## 🧩 What Is a **Cluster Network (or Cluster Placement Group)**?

A **Cluster Placement Group** in AWS is a way to **launch EC2 instances very close to each other — physically** — inside the same **Availability Zone (AZ)** and **network segment**.

It’s designed to give your instances:

- **Very high network bandwidth** (up to 100 Gbps+)
    
- **Very low latency**
    
- **High packet-per-second performance**
    

---

### 🧠 Think of it like this:

> Normally, EC2 instances in a VPC could be placed anywhere in an Availability Zone (on different racks).
> 
> A **cluster placement group** tells AWS:  
> “Put my instances right next to each other on the same rack or subnet so they can talk super fast.” ⚡

---

## 📡 Use Case Examples

|Use Case|Why Cluster Helps|
|---|---|
|**High-performance computing (HPC)**|Needs fast node-to-node communication|
|**Big data analytics (Spark, Hadoop)**|Reduces network bottlenecks between nodes|
|**Machine learning training clusters**|Enables faster distributed training|
|**Real-time simulation or rendering**|Requires ultra-low latency|

---

## ⚙️ How It Works

When you create a cluster placement group:

1. AWS reserves a **contiguous block of underlying hardware** in one AZ.
    
2. You **launch instances into that group** using the same instance type.
    
3. Those instances are connected with **enhanced networking adapters** and **high-speed links** (like Elastic Fabric Adapter or EFA).
    

---

### Example CLI Command

```bash
aws ec2 create-placement-group \
    --group-name myClusterGroup \
    --strategy cluster
```

Then when you launch instances:

```bash
aws ec2 run-instances \
    --image-id ami-xxxxxx \
    --count 4 \
    --instance-type c5n.18xlarge \
    --placement GroupName=myClusterGroup
```

All 4 instances will now live close together for **maximum network performance**.

---

## 🧮 Network Speed Comparison

|Placement|Latency|Bandwidth|Use Case|
|---|---|---|---|
|**Cluster**|🔥 Lowest|🔥 Highest|HPC, ML, analytics|
|**Spread**|High|Normal|Fault-tolerant, separate racks|
|**Partition**|Medium|Moderate|Big data like HDFS|

So AWS actually has **three placement strategies**:

1. **Cluster** → High performance, same rack
    
2. **Spread** → High availability, different racks
    
3. **Partition** → Data separation (for large-scale apps)
    

---

## ⚠️ Limitations

- Must be in **one Availability Zone**
    
- **Same instance type** recommended
    
- Limited by AWS capacity in that AZ
    
- If you try to add more instances later and capacity is full → you’ll get a **“InsufficientInstanceCapacity”** error
    

---

## ✅ In summary:

> A **Cluster Network (Cluster Placement Group)** is a special EC2 networking setup that places instances close together in the same AZ for **ultra-fast, low-latency** communication — ideal for HPC, ML, and big data workloads.



## Spread Placement Group.
---

## 🧩 What Is a **Spread Placement Group**?

A **Spread Placement Group (SPG)** in AWS is a way to **launch EC2 instances across different underlying hardware (racks)** within a Region or Availability Zone to **reduce the risk of simultaneous failure**.

In simple terms:

> It spreads your instances apart (on different physical racks, power, and network paths) — so if one rack fails, others keep running. ⚙️

---

## 🧠 Think of it like this:

> Cluster = put instances **together** for speed  
> Spread = put instances **apart** for safety ✅

---

## ⚙️ How It Works

- Each instance in a **Spread Placement Group** is placed on **distinct hardware**.
    
- You can spread instances **across multiple Availability Zones** in the same Region.
    
- Designed for **critical workloads** that require **high availability**.
    

---

## 💼 Example Use Cases

|Use Case|Why Use Spread Placement|
|---|---|
|Critical databases|Protects against single rack failure|
|Key microservices|Ensures availability during hardware failure|
|Small, independent workloads|Adds resilience without complex architecture|

---

## ⚙️ Example CLI

```bash
aws ec2 create-placement-group \
    --group-name mySpreadGroup \
    --strategy spread
```

Then launch instances into it:

```bash
aws ec2 run-instances \
    --image-id ami-xxxxxx \
    --count 7 \
    --instance-type t3.medium \
    --placement GroupName=mySpreadGroup
```

> Note: You can have **up to 7 instances per AZ** in a spread placement group.

---

## 🧮 Quick Comparison

|Placement Type|Goal|Physical Location|Use Case|
|---|---|---|---|
|**Cluster**|Performance|Same rack|HPC, ML, analytics|
|**Spread**|Availability|Different racks|Databases, critical apps|
|**Partition**|Isolation|Grouped sets of racks|Hadoop, Cassandra, HDFS|

---

## ✅ In short:

> A **Spread Placement Group** spreads your EC2 instances across multiple racks and hardware to **maximize fault tolerance** — so even if one rack or server fails, your other instances stay running.



## Partition Placement
---
## 🧩 What Is a **Partition Placement Group (PPG)**?

A **Partition Placement Group** is designed for **large distributed systems** like big data, Hadoop, Cassandra, or HDFS.

It divides your EC2 instances into **logical partitions**, and **each partition is isolated** from the others at the **hardware level** — meaning:

> Instances in different partitions do **not share racks, power sources, or network switches**.

So, a failure in one partition won’t affect instances in another. ⚡

---

## 🧠 Think of it like this:

|Placement|Idea|Analogy|
|---|---|---|
|**Cluster**|All together for speed|Players on the same bench 🏃‍♂️🏃‍♀️|
|**Spread**|All apart for safety|Players in different stadiums 🏟️|
|**Partition**|Groups of together-apart|Teams in different stadiums, each with players close together ⚙️|

---

## ⚙️ How It Works

- You define **how many partitions** you want (up to 7 per Availability Zone).
    
- AWS automatically places each partition’s instances on **separate racks**.
    
- Within a partition, instances can communicate **quickly**.
    
- Between partitions, communication is still available but **isolated for safety**.
    

---

## 💼 Example Use Cases

|Use Case|Why Use Partition Placement|
|---|---|
|**Hadoop clusters**|Protect data replicas on different hardware|
|**Cassandra databases**|Prevents node failures from affecting entire cluster|
|**Big data analytics**|Combines performance & fault isolation|

---

## ⚙️ Example CLI

```bash
aws ec2 create-placement-group \
    --group-name myPartitionGroup \
    --strategy partition \
    --partition-count 3
```

Then launch instances into it:

```bash
aws ec2 run-instances \
    --image-id ami-xxxxxx \
    --count 6 \
    --instance-type m5.xlarge \
    --placement GroupName=myPartitionGroup
```

AWS automatically splits them into 3 partitions, 2 instances each.

---

## 🧮 Comparison Summary

|Type|Goal|AZ Scope|Physical Layout|Max Instances|Ideal For|
|---|---|---|---|---|---|
|**Cluster**|Performance|1 AZ|Same rack|Limited by capacity|HPC, ML|
|**Spread**|Availability|Multi-AZ|Different racks|7 per AZ|Critical apps|
|**Partition**|Scale + Isolation|1 AZ|Separate partitions|Large (hundreds)|Big data, NoSQL|

---

## ✅ In short:

> A **Partition Placement Group** lets you run large, distributed systems where instances are grouped into partitions that are **isolated for fault tolerance**, but still **close enough** for performance within each group.
