---

## 🧩 **What Is a Security Group in AWS?**

A **Security Group (SG)** is a **virtual firewall** for your EC2 instances that **controls inbound and outbound traffic** at the **instance level**.

Think of it as a **set of rules** that decide:

> “Who can talk to my instance, and who can my instance talk to?” 🔐

---

## ⚙️ How It Works

Each **EC2 instance** is associated with one or more **security groups**.

- **Inbound rules** → define what traffic is **allowed _to_** your instance.
    
- **Outbound rules** → define what traffic is **allowed _from_** your instance.
    

All other traffic (not explicitly allowed) is **denied by default**.

---

### 🧠 Example:

You launch a web server on EC2:

- Inbound: Allow TCP port **80** (HTTP) from anywhere (0.0.0.0/0)
    
- Inbound: Allow TCP port **22** (SSH) from your IP only
    
- Outbound: Allow **all** (default)
    

✅ Result:

- Anyone can access your website on port 80
    
- Only you can SSH into it
    
- The server can make outgoing connections (e.g., update packages)
    

---

## 🧾 Example Security Group Rules

|Direction|Protocol|Port|Source/Destination|Description|
|---|---|---|---|---|
|Inbound|TCP|22|Your IP|SSH Access|
|Inbound|TCP|80|0.0.0.0/0|HTTP Access|
|Outbound|All|All|0.0.0.0/0|Allow all outbound traffic|

---

## 🧠 Key Characteristics

|Property|Description|
|---|---|
|**Stateful**|If inbound traffic is allowed, the response is automatically allowed.|
|**Default deny**|All traffic is denied unless explicitly allowed.|
|**Instance-level**|Applies to EC2 instances (not subnets).|
|**Multiple groups**|You can attach multiple security groups to one instance.|

---

## 🔒 Security Group vs Network ACL

|Feature|Security Group|Network ACL|
|---|---|---|
|**Scope**|Instance-level|Subnet-level|
|**Stateful**|✅ Yes|❌ No|
|**Default behavior**|Deny all|Allow all|
|**Use case**|Control access to specific EC2s|Control traffic at subnet boundary|

---

## ✅ In Short:

> A **Security Group** is an **instance-level firewall** that defines what network traffic is allowed **to and from** your AWS resources like EC2.
> 
> It’s your **first line of defense** for securing instances in a VPC.

# 🧱 **AWS Network Access Control List (NACL)** — Notes

---

## 🔹 **Definition**

A **Network Access Control List (NACL)** is a **stateless, subnet-level firewall** that controls **inbound and outbound traffic** to and from subnets in your **VPC (Virtual Private Cloud)**.

Think of it as an **extra security layer** for your entire subnet — controlling what traffic can **enter or leave** that subnet.

---

## 🔹 **Key Characteristics**

|Feature|Description|
|---|---|
|**Scope**|Works at the **subnet level** (applies to all instances in that subnet)|
|**Type**|**Stateless** — checks every packet both ways|
|**Rules**|Can **allow** or **deny** traffic|
|**Default behavior**|The **default NACL** allows all inbound and outbound traffic|
|**Custom NACL**|Denies all inbound and outbound traffic until rules are added|
|**Order**|Rules are evaluated in **ascending order** (by rule number)|
|**Attached to subnet**|Each subnet must be associated with exactly **one NACL** (but one NACL can be shared across multiple subnets)|

---

## 🔹 **How It Works**

When traffic enters or leaves a subnet:

1. AWS checks the **Network ACL** first.
    
2. The ACL applies **inbound rules** for traffic entering the subnet.
    
3. It applies **outbound rules** for traffic leaving the subnet.
    
4. Each packet is evaluated against rules in order — the **first match wins**.
    
5. If no rule matches, the traffic is **denied by default**.
    

---

## 🔹 **Stateless Nature**

- NACLs **do not remember** previous connections.
    
- You must explicitly allow **inbound and outbound** traffic for a two-way conversation.
    
- Even if inbound is allowed, the **response** will be blocked unless outbound is allowed too.
    

🧠 **Example:**  
If you allow inbound HTTP (port 80), you must also allow outbound ephemeral ports (1024–65535) for return traffic.

---

## 🔹 **Rule Structure**

Each NACL rule has:

|Field|Description|
|---|---|
|**Rule number**|Determines evaluation order (lowest first)|
|**Type**|Protocol (e.g., HTTP, SSH, ALL traffic)|
|**Protocol**|e.g., TCP, UDP, ICMP|
|**Port range**|Specific port or range (e.g., 22, 80, 443, 1024–65535)|
|**Source/Destination**|IP address or CIDR range|
|**Allow/Deny**|Action to take on matching packets|

---

## 🔹 **Example Rules**

|Rule #|Type|Direction|Protocol|Port|Source/Destination|Action|
|---|---|---|---|---|---|---|
|100|Inbound|TCP|80|0.0.0.0/0|ALLOW||
|110|Inbound|TCP|22|203.0.113.25/32|ALLOW||
|120|Inbound|ALL|ALL|0.0.0.0/0|DENY||
|100|Outbound|ALL|ALL|0.0.0.0/0|ALLOW||

---

## 🔹 **Default NACL vs Custom NACL**

|Feature|**Default NACL**|**Custom NACL**|
|---|---|---|
|Inbound rules|Allow all|Deny all|
|Outbound rules|Allow all|Deny all|
|Automatically associated?|Yes (new subnets)|No|
|Can modify rules?|✅ Yes|✅ Yes|

---

## 🔹 **Best Practices**

1. ✅ Use **Security Groups** for instance-level protection.
    
2. ✅ Use **NACLs** for **additional subnet-level filtering** (e.g., block specific IPs).
    
3. ⚙️ Always **allow both inbound and outbound** rules for bidirectional communication.
    
4. 🧱 Leave the **default NACL** open if you rely only on Security Groups — but **tighten** it for public-facing subnets.
    
5. 🔢 Keep **rule numbers organized** (e.g., increments of 10 for future rules).
    

---

## 🔹 **Comparison: NACL vs Security Group**

|Feature|**Network ACL (NACL)**|**Security Group (SG)**|
|---|---|---|
|**Level**|Subnet|Instance|
|**State**|Stateless|Stateful|
|**Rules**|Allow + Deny|Allow only|
|**Default behavior**|Allow all (default NACL)|Deny all inbound, allow all outbound|
|**Return traffic**|Must define both directions|Automatically allowed|
|**Evaluation order**|Rule number sequence|All rules evaluated together|
|**Attached to**|Subnet|EC2 instance|
|**Use case**|Broad subnet-level filtering|Fine-grained instance control|
