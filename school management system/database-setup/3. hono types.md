Since you have `verbatimModuleSyntax: true` enabled in your `tsconfig.json`, TypeScript is being very strict. It requires you to explicitly distinguish between **runtime code** (classes/functions) and **type-only declarations** (interfaces/types) during imports.

Because `Context` and `Next` are used only as types in your middleware and utilities, they must be imported using the `import type` syntax.

### 1. Fix for the Middleware

Update your middleware to use the `type` keyword. This ensures that when the code is compiled to JavaScript, these imports are completely stripped out, preventing "missing export" errors at runtime.

**`src/middleware/tenant.middleware.ts`**

TypeScript

```
import type { Context, Next } from "hono";
import { AppError } from "../utils/response.js";

export const tenantMiddleware = async (c: Context, next: Next) => {
  const schoolId = c.req.header("x-school-id");
  
  if (!schoolId) {
    throw new AppError("School context is required", 401);
  }

  // Set the schoolId in Hono's context for use in Services
  c.set("schoolId", schoolId);
  
  await next();
};
```

---

### 2. Fix for the Response Utility

The same rule applies to any utility where you pass the Hono context around.

**`src/utils/response.ts`**

TypeScript

```
import type { Context } from "hono";

export const sendResponse = (c: Context, data: any, message = "Success", status = 200) => {
  return c.json({
    success: true,
    message,
    data,
    schoolId: c.get("schoolId"),
  }, status as any);
};

export class AppError extends Error {
  constructor(public message: string, public statusCode: number = 400) {
    super(message);
  }
}
```

---

### 3. Pro-Tip: Hono Type Safety

To make your "Never Seen Before" system even more robust, you can define your environment types (like `schoolId`) globally. This prevents you from having to remember string keys like `c.get("schoolId")`.

**`src/types/hono.ts`**

TypeScript

```
export type Env = {
  Variables: {
    schoolId: string;
    userRole: string;
  };
};
```

Then, in your routes/middleware, you use it like this:

TypeScript

```
import { Hono } from "hono";
import type { Env } from "./types/hono.js";

const app = new Hono<Env>();

app.get("/test", (c) => {
  const schoolId = c.get("schoolId"); // Now type-safe!
  return c.text(`School ID is ${schoolId}`);
});
```

### Why `verbatimModuleSyntax` requires this:

When you use modern ESM (ES Modules), some tools struggle to know if an import like `import { Context }` is a class (which needs to stay in the code) or an interface (which needs to be deleted). By writing `import type`, you are telling the compiler: _"This is purely for my eyes and the IDE; don't include this in the final `.js` file."_
