For a large-scale school management system, choosing the right multi-tenancy strategy is the most critical architectural decision you will make. It affects security, database performance, and how you write your Drizzle queries.

Since you are building a **Modular Monolith** with **Hono and Drizzle**, there are three main strategies. I’ll break them down and give you my recommendation.

---

### 1. The Three Multi-Tenancy Strategies

|**Strategy**|**How it works**|**Pros**|**Cons**|
|---|---|---|---|
|**Shared Schema (Column-based)**|Every table has a `school_id`. Every query includes `WHERE school_id = '...'`.|Easiest to maintain; cheapest to host; simple migrations.|Risk of "data leakage" if a developer forgets a `WHERE` clause.|
|**Schema-per-Tenant**|Each school gets its own PostgreSQL **Schema** (e.g., `school_a.students`, `school_b.students`).|Stronger isolation; easy to back up one school's data.|Migrations become a nightmare (running 100 migrations for 100 schools).|
|**Database-per-Tenant**|Each school gets a completely separate DB instance/URI.|Maximum security; no resource contention.|Very expensive and complex to manage at scale.|

---

### 2. The Recommended Path: Shared Schema + Row Level Security (RLS)

For a school management system where you might have hundreds of small-to-medium schools, the **Shared Schema** approach is the industry standard—**but only when paired with PostgreSQL Row Level Security (RLS).**

By using PostgreSQL RLS, the database itself ensures that `School A` can never see `School B`'s data, even if your Hono code is buggy.

#### Step 1: Update your Schemas

Every table in your `src/db/schema/` must now include a `schoolId`.

TypeScript

```
// src/db/schema/users/students.ts
import { pgTable, text, integer, uuid } from "drizzle-orm/pg-core";
import { schools } from "../admin/schools"; // A new table to track schools

export const students = pgTable("students", {
  id: text("id").primaryKey(),
  schoolId: uuid("school_id").notNull().references(() => schools.id), // The "Tenant Key"
  name: text("name").notNull(),
  // ... other fields
});
```

#### Step 2: Hono Middleware for Tenant Identification

You need to identify which school is making the request. Usually, this is done via a custom domain (`school-a.platform.com`) or a header.

TypeScript

```
// src/middleware/tenant.middleware.ts
import { Context, Next } from "hono";

export const tenantMiddleware = async (c: Context, next: Next) => {
  const schoolId = c.req.header("x-school-id"); // Or extract from JWT/Domain
  
  if (!schoolId) {
    return c.json({ error: "School Context Missing" }, 400);
  }

  // Set the schoolId in Hono context to use in Services
  c.set("schoolId", schoolId);
  
  // OPTIONAL: Tell Postgres which school is active for this session (RLS)
  // await db.execute(sql`SET app.current_school_id = ${schoolId}`);
  
  await next();
};
```

#### Step 3: Enforcing Tenant Isolation in Services

Instead of manually adding `.where(eq(table.schoolId, schoolId))` to every single query, you can wrap your Drizzle calls.

TypeScript

```
// src/modules/users/students/student.service.ts
import { db } from "../../../db";
import { students } from "../../../db/schema/users/students";
import { and, eq } from "drizzle-orm";

export class StudentService {
  static async getStudentsBySchool(schoolId: string) {
    return await db.select()
      .from(students)
      .where(eq(students.schoolId, schoolId)); // Always filter by tenant!
  }
}
```

---

### 3. Why this works for "Large Scale"

1. **Unified Migrations:** When you add a "bloodType" column to the `Student` table, you run **one** migration, and it applies to all schools instantly.
    
2. **Shared Resources:** One database connection pool handles all schools, saving memory and money.
    
3. **Global Analytics:** As the "Super Admin," you can easily run reports across all schools (e.g., "Total students in the system") because they are in one table.
    

### The "Safety Net"

If you are worried about human error (forgetting a `where` clause), you can use **PostgreSQL Policies**. You create a policy that says:

> "Users can only see rows in this table where `school_id` matches their session variable."

This way, even if your Drizzle query is `db.select().from(students)`, Postgres will automatically filter it to only show the current school's students.
